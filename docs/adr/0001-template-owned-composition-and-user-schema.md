# ADR-0001：由宿主模板拥有模块组合和用户模型

## 状态

已接受

## 背景

本仓库要服务约十个可独立演进的 SaaS。登录、支付、邮件和邀请等能力高度相似，
适合复用；但每个 SaaS 启用的能力、服务商、用户字段和事件后的业务规则不同。

原来的 `stacks/saascore` 同时选择服务商、迁移统一 `users` 表、组装所有模块并执行
跨模块规则。这让新项目启动很快，却把共享代码升级和宿主数据库结构绑定在一起：
一个 SaaS 增加用户字段或替换支付、邮件服务商时，容易影响其他 SaaS。

我们需要同时满足：

- 新 SaaS 能快速启用或关闭邮箱登录、OAuth、支付和邀请；
- 共享模块不依赖任何项目的完整用户模型；
- 注册、登录、支付等事件由当前 SaaS 自己组合；
- 某个 SaaS 修改用户字段时，不要求其他 SaaS 升级或迁移；
- 默认方案足够简单，单进程和进程内事件总线即可启动；
- 支付 Webhook 保持幂等，认证和个人信息等敏感数据不跨边界泄漏。

## 决策

采用“共享能力模块 + 宿主组合根”的模块化单体：

```text
foundation/*                 通用技术能力
modules/*                    独立业务能力、端口和可选适配器
templates/quickstart/
  internal/user/             当前 SaaS 拥有的用户模型与仓储
  internal/platform/         模块实例、路由和服务商选择
  internal/bootstrap/        启动、迁移和事件订阅
  internal/feature/*         当前 SaaS 的具体业务
```

具体规则如下：

1. `modules/auth` 只依赖 `auth/port.UserStore`，不拥有 `users` 表。
2. `modules/billing` 只通过最小账户投影读取用户 ID 和邮箱；支付标识及订阅快照存入
   billing 自己的表。
3. `modules/referral` 只保存用户 ID 和邀请关系；奖励数值和发放方式由宿主监听器决定。
4. 邮件和 OAuth、支付服务商在 `templates/quickstart` 中选择并注入；替换服务商只改
   当前 SaaS 的组装代码。
5. `UserSignedUp`、`UserLoggedIn`、支付和邀请事件由模板直接订阅。欢迎邮件、注册奖励、
   邀请归因等规则写在宿主监听器中，不写回共享模块。
6. 用户表和它的数据库迁移属于复制后的 SaaS。共享仓库不再提供或自动迁移一个
   代表所有项目的完整 `User` 模型。
7. 模块只迁移自己拥有的表；模板显式决定启用了哪些模块，并只迁移相应模块的表。

## 结果

### 正面影响

- 修改一个 SaaS 的用户字段不会传播到其他 SaaS。
- 同一个模块可以搭配 Google、GitHub 或未来的身份服务商，也可以搭配不同邮件、支付适配器。
- 模块之间通过事件和端口协作，宿主业务规则的位置清晰并且容易测试。
- quickstart 仍然提供一套可运行的默认组合，新项目不需要从零搭建。

### 负面影响

- 复制模板后，宿主需要维护自己的用户迁移和少量适配代码。
- 模板升级不再等同于依赖升级；已经分叉的 SaaS 需要选择性合并模板改动。
- 进程内事件监听器的错误只会被记录，不能把失败返回给已经完成的注册、登录或
  Webhook；需要可靠送达的副作用必须由宿主写入 outbox 并异步重试。

### 中性影响

- 当前继续使用模块化单体和同一个 PostgreSQL，不引入消息队列或微服务。
- 当可靠异步副作用成为真实需求时，可以在宿主监听器后增加 outbox，而不改变模块端口。

## 考虑过的替代方案

### 保留强制 `saascore`

启动最省代码，但会继续统一用户结构和服务商选择，无法满足独立演进要求。

### 每个 SaaS 复制全部模块

灵活性最高，但登录、支付和 Webhook 修复无法复用，十个项目会迅速产生重复维护。

### 立即拆成微服务

隔离更强，但部署、可观测性、消息一致性和运维成本明显超出当前规模，不采用。
