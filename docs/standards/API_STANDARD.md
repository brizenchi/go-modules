# API 设计规范（HTTP / JSON）

项目具体使用的响应工具、路由分组等实现细节，记录在 [PROJECT.md](./PROJECT.md)。

## 路径

| 规则 | 示例 |
| --- | --- |
| 统一前缀和版本：`/api/v1` | `/api/v1/account/profile` |
| 资源用名词；多个单词用 `-`；集合用复数 | `/api/v1/invoices`、`/api/v1/credit-transactions` |
| 嵌套最多两层 | `/api/v1/notes/:id/export` |
| 动作无法用 HTTP 方法表达时，用动词子路径 | `/api/v1/subscription/cancel` |
| 后台管理接口单独分组 | `/api/v1/admin/*` |
| 第三方回调（Webhook、OAuth）使用固定路径 | `/api/v1/stripe/webhook` |

## HTTP 方法

| 方法 | 用途 | 幂等 |
| --- | --- | --- |
| `GET` | 查询，不能有副作用 | 是 |
| `POST` | 创建资源或执行动作 | 否，需要时使用 `Idempotency-Key` |
| `PATCH` | 部分更新 | 是 |
| `PUT` | 整体替换（少用） | 是 |
| `DELETE` | 删除 | 是 |

## 请求头

| 请求头 | 说明 |
| --- | --- |
| `Authorization: Bearer <token>` | 用户身份 |
| `Content-Type: application/json` | 请求体统一用 JSON（文件上传除外） |
| `X-Request-ID` | 可选。客户端传入或服务端生成，**响应头里一定返回** |
| `Idempotency-Key` | 有副作用且可能被重复提交的写操作需要 |
| `traceparent` | W3C 链路上下文，服务之间调用时自动传递 |

## 响应格式

整个 API 只使用一种响应格式。推荐的外壳：

```json
{ "code": 200, "msg": "ok", "data": { } }
```

- `code` 和 HTTP 状态码保持一致；
- 只有 Webhook、文件下载、重定向这类必须遵守外部协议的接口可以不使用外壳。

## 错误

| HTTP | 何时使用 |
| --- | --- |
| 400 | 参数不合法、格式错误、业务规则不允许 |
| 401 | 未登录，或者 token 无效、已过期 |
| 403 | 已登录但没有权限 |
| 404 | 资源不存在。**访问别人的资源也返回 404**，不暴露资源是否存在 |
| 409 | 状态冲突：重复创建、版本冲突、幂等键被不同的请求体使用 |
| 422 | （可选）语义校验失败；与 400 二选一，全项目保持一致 |
| 429 | 超出频率限制 |
| 500 | 未知错误，返回固定文案，不返回内部细节 |
| 503 | 功能未启用，或依赖暂时不可用 |

### `reason`：给程序判断用的稳定错误原因

前端需要根据错误做不同处理时，在 `data` 中返回稳定的 `reason`：

```json
{ "code": 400, "msg": "auth: invalid or expired verification code", "data": { "reason": "AUTH_INVALID_CODE" } }
```

- 格式 `<模块>_<原因>`，全大写，用下划线连接；**发布后不能修改**；
- `msg` 给开发者看（英文），前端**不直接展示**；用户看到的文案由前端根据 `reason` 和多语言配置决定。

### 安全
- 500 不返回异常信息；登录失败不区分"用户不存在"和"密码错误"；
- 内部细节只写进日志，用户凭 `X-Request-ID` 反馈问题。

## 数据格式

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 字段名 | 全项目一种风格（推荐小写加下划线） | `created_at` |
| 时间 | RFC 3339，**UTC** | `"2026-10-06T03:19:30Z"` |
| **金额** | **整数，最小货币单位**，同时返回币种 | `{"amount": 1999, "currency": "usd"}` |
| ID | 字符串 | `"8f2c…"` |
| 枚举 | 小写加下划线的字符串 | `"period_end"` |
| 空值 | 同一个字段统一用 `null` 或省略 | |

## 分页、筛选、排序

```text
GET /api/v1/invoices?page=1&limit=20&status=paid&sort=-created_at
```

```json
{ "code": 200, "msg": "ok", "data": { "items": [], "total": 135, "page": 1, "limit": 20 } }
```

- `page` 从 1 开始；`limit` 默认 20，**最大 100**；
- 排序必须稳定（例如 `created_at DESC, id DESC`）；只开放有索引的字段；`-` 表示倒序；
- 大数据量或实时滚动的列表使用游标分页（`cursor` / `next_cursor`），在接口文档中注明；
- 搜索关键词使用 `q`，限制最大长度。

## 幂等

- 创建订单、发放额度、修改关键配置这类**重试会造成损失**的接口，要求 `Idempotency-Key`；
- 服务端保存"key → 请求摘要 → 结果"：相同的 key 和请求体返回同一个结果，请求体不同返回 409；
- Webhook 按事件 ID 去重。

## 认证、限流、CORS

- 鉴权在路由分组或中间件统一完成；资源归属在业务层**再检查一次**（见 [SECURITY_STANDARD.md](./SECURITY_STANDARD.md#鉴权与越权)）；
- 登录、验证码等容易被滥用的接口限流，超出返回 429；
- CORS 只允许白名单域名，不使用 `*`。

## 兼容性

- 同一个大版本内**只做增量修改**：可以新增字段、接口、可选参数；
- 不删除、不重命名字段，不改变类型和含义，不把可选参数改成必填；
- 必须破坏兼容时，新增 `/api/v2/...`，旧接口至少保留一个发布周期，并返回 `Deprecation` 响应头；
- 前后端分开部署时，保证"先部署后端、后部署前端"的中间状态也能正常工作。

## 接口契约

- 修改接口时，调用方（前端、其他服务、SDK）的类型在**同一个 PR** 里更新；
- 推荐用 OpenAPI 作为契约：由代码生成规范文件，调用方根据它生成类型，CI 检查生成结果是否最新。
