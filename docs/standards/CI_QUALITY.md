# CI quality gates and dependencies

## Who checks what

**CI is the single source of truth**: every check runs in GitHub Actions, and nothing
merges until they pass. Locally we keep only what must happen before code leaves the machine.

| Where | When | Checks | Configuration |
| --- | --- | --- | --- |
| Editor / AI assistant | after editing a file | formatting; blocks commands that bypass checks | `.editorconfig` `.claude/settings.json` |
| Local Git hooks | `git commit` | **secret scan** gofmt | `lefthook.yml` |
| CI | every pull request and push to `main` | everything | `.github/workflows/keel.yml` and the project's own workflows |

Why so little runs locally:

- **Secret scanning**: CI runs after the push, and a pushed secret must be treated as leaked, so it can only be stopped locally.
- **Formatting**: takes under a second and saves a CI round trip.
- Tests, lint, commit messages and everything else run in CI; repeating them locally only slows commits down.

## Local hooks

Each developer installs them once:

```bash
brew install lefthook gitleaks      # or follow each tool's install instructions
keel hooks                          # same as lefthook install
```

Do not skip hooks with `git commit --no-verify`; the Claude Code hooks block AI assistants from running it.

## What CI runs

`.github/workflows/keel.yml` is generated by [keel](https://github.com/brizenchi/keel) and calls keel's versioned (`@v2`) reusable workflows:

| Check | What it does |
| --- | --- |
| `commits / pr-title` | the pull request title follows Conventional Commits (it becomes the squash commit) |
| `secrets / gitleaks` | scans the full Git history for secrets |
| `go-* / check` | gofmt, go vet, go test -race |
| `go-* / lint` | golangci-lint |
| `go-* / vuln` | govulncheck (**does not block merging**) |
| `node-* / check` | installs dependencies and runs the configured scripts (default: lint, test, build) |
| `node-* / audit` | audit of production dependencies (**does not block merging**) |

This project uses `ci_mode=reusable`: `keel.yml` is called by the `keel` job in the
project's own workflow, so check names start with `keel / ` and later jobs such as
deployments can declare `needs: keel`.

The project's own checks (builds, end-to-end tests, deployments) live in other workflow
files; keel never changes them.

Vulnerability scans do not block merging: a newly published advisory in a dependency must
not hold up an unrelated urgent fix. When they report something, follow "Vulnerabilities" below.

## Required checks

The checks that must pass before merging are listed in `.keel/required-checks.txt`, and
`keel github` writes them into the branch ruleset. Append the checks of your own workflows
to that file and run `keel github` again.

When CI fails, reproduce it locally instead of re-running and hoping. Fix flaky tests or
open an issue to track them.

## Dependencies

### Automatic updates
`.github/dependabot.yml` checks dependencies weekly and groups minor and patch updates
into one pull request; GitHub Actions are checked monthly.

- Patch and minor updates: merge when CI passes.
- Major updates: read the release notes and handle them separately.
- Update related packages (sub-packages of one framework) together.

### Adding a dependency
State in the pull request:

1. why it is needed, and why the standard library or existing dependencies are not enough;
2. how well it is maintained: latest release, whether issues get answered;
3. its license: MIT, BSD and Apache-2.0 are fine; discuss GPL, AGPL and others first;
4. how many transitive dependencies it brings. Shared libraries stay lightweight.

### Vulnerabilities
- Fix high-severity findings within a week, or record why the project is not affected.
- Dependabot security alerts and security updates are enabled by `keel github`.

## Managing keel

```bash
keel status                    # version, components, hooks, GitHub settings
keel update                    # move to a newer release, keeping local edits
keel config                    # answer all questions again
keel enable ai / keel disable dependabot      # turn components on or off
keel add go_modules dir=services/api          # check another directory
```

Each command lists the files it changed; review them with `git diff` and commit
(`chore: update keel`). Change languages, directories and components through these
commands rather than editing the job list in `keel.yml` by hand.
