# 故障响应与复盘

## 严重级别

| 级别 | 定义 | 示例 | 响应要求 |
| --- | --- | --- | --- |
| **P1** | 核心功能不可用，或者有数据、资金、安全方面的损失 | 全站无法访问；支付后没有开通；密钥泄露 | 立即处理，直到恢复；每 30 分钟同步一次进展 |
| **P2** | 部分功能不可用，或者明显变差，有临时绕过办法 | 某一种登录方式失败；邮件延迟；P99 超过 5 秒 | 当天处理 |
| **P3** | 影响很小 | 后台某个页面报错；个别用户的问题 | 排进正常的开发计划 |

告警规则里的 `severity: critical` 对应 P1 或 P2，`warning` 对应 P3（见 `deploy/alerts/rules.yaml`）。

## 处理流程

```text
发现 → 确认级别 → 止血 → 定位 → 修复 → 确认恢复 → 复盘
```

### 1. 发现与确认
- 来源：Grafana 告警、用户反馈、发布后检查；
- 打开 Grafana，确认影响范围：哪个服务、哪些接口、从什么时候开始、影响多少用户；
- 定好级别，在团队频道里发一条消息："P1/P2：<现象>，<负责人> 正在处理"。

### 2. 止血（优先于找到根因）
| 情况 | 止血方法 |
| --- | --- |
| 刚发布完就出了问题 | **立即回滚**（见 [DEPLOYMENT.md](./DEPLOYMENT.md#回滚)） |
| 某个第三方服务出问题 | 关闭依赖它的功能，或者切换到备用服务商（比如邮件切换到另一个服务商） |
| 某个功能有缺陷 | 用配置开关关闭这个功能 |
| 密钥泄露 | 立即作废并轮换（见 [SECURITY_STANDARD.md](./SECURITY_STANDARD.md#密钥泄露处理)） |
| 流量异常 | 在入口层限流或者封禁来源 |

### 3. 定位
用可观测性数据逐步缩小范围：

1. **指标**：错误率和延迟在什么时间开始变化？是哪个接口？和哪次发布或者哪个第三方服务有关？
2. **链路**：在 Tempo 里查询 `{ resource.service.name = "<服务>" && status = error }`，看是哪一步出错，或者哪一步变慢；
3. **日志**：从链路跳转到这次请求的日志，看具体的错误信息；
4. 用户反馈的问题：让用户提供 `X-Request-ID`（浏览器开发者工具的响应头里可以看到；前端错误提示也应该显示它，见 [FRONTEND.md](./FRONTEND.md#请求规范)），直接查到这次请求。

### 4. 修复与确认
- 按 [GIT_WORKFLOW.md](./GIT_WORKFLOW.md#紧急修复hotfix) 走紧急修复流程；
- 确认指标恢复正常、告警恢复后，在团队频道里通知"已恢复"；
- 涉及数据错误（比如积分多发、订阅状态不对）时，先修正数据，修正过程要记录下来。

### 5. 和用户沟通
- P1 或者影响付费用户的 P2，主动告知受影响的用户：发生了什么、影响是什么、现在的状态；
- 涉及用户数据泄露时，按适用的法律法规通知用户。

## 复盘

P1、P2 在恢复后 **3 个工作日内**完成复盘，文档放在 `docs/incidents/YYYY-MM-DD-<简述>.md`。

复盘的原则：**对事不对人**。目标是改进流程和系统，不是追究个人责任。

### 复盘模板

```markdown
# <日期> <一句话描述>

- 级别：P1 / P2
- 持续时间：<开始> ～ <恢复>（共 X 分钟）
- 负责人：

## 影响
多少用户、哪些功能、有没有数据或资金损失。

## 时间线
| 时间（UTC） | 事件 |
| --- | --- |
| 10:02 | 告警 HighServerErrorRate 触发 |
| 10:05 | 确认为 P1，开始处理 |
| 10:09 | 回滚到上一个版本，错误率恢复 |

## 根本原因
不停追问"为什么"，直到找到流程或系统层面的原因。

## 做得好的地方 / 需要改进的地方

## 改进项
| 改进项 | 负责人 | 截止日期 | issue |
| --- | --- | --- | --- |
| 补充 xxx 的告警 | | | |
| 增加回归测试 | | | |
```

## 值班（团队扩大后）

单人维护时由维护者负责所有告警。多人协作后：

- 按周轮流值班，在 Grafana 的告警通知策略里配置值班人；
- 交接时说明本周的告警、未处理的问题和计划中的发布。
